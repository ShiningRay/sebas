### B.3 里程碑门禁（M-gate）

每期 M-gate 须**全部**满足（缺一不过）：

1. 该期全部 WP 验收标准逐条有可复现证据（命令输出/spec 通过记录）。
2. design.md §14 该期验收条目逐条勾稽（[WBS 各包](../wbs/README.md) 已逐条映射，验收时按勾稽表核对）。
3. 质量三命令：`crystal spec` 0 fail、`./bin/ameba` 无警告、`make release` 成功 [来源: 仓库:CONTRIBUTING.md 质量门禁节]。
4. docs 同步：实现行为与 design.md/本文档一致，偏差处回写设计文档（[CONTRIBUTING.md](../../../../CONTRIBUTING.md) 的 Design-first changes 节）。
5. 风险复核：该期新增风险/未验证项进入 §15.1 口径记录（回写 design.md）。

阶段门禁 Go/No-Go 判据：M0 若强杀恢复不达标 → No-Go 返工 WP3/WP8；M1 若双账号串扰 → No-Go 返工 WP1（不接受「演示绕过」）；M3 若 mrb.cr 复核不可用**或 Windows 新 mruby.exe 链接环境 blocker 未消项**（恢复路径见 [review/m3-plugin-feasibility.md](../../review/m3-plugin-feasibility.md)）→ WP4~WP6 降级为技术预研 Go，降级证据 = 可行性报告与本机链接失败复现记录，产品化验收延至 blocker 消项后重跑（见 M3-WP4 风险）。[推演]

**M4 期门禁口径（Q7 裁断，2026-11-20 追加）**：M4.0–M4.4 各期 M-gate 沿用上述五项框架（§14 勾稽/docs 同步/质量命令/风险复核照旧），第 3 条质量命令改为「调度四条」全绿：`make format-check` + `make spec` + `make lint` + `make release` [来源: 仓库:docs/design/proposals/session-input-scheduling.md §9 验收与门禁（原文作 `make spec`）]；纯文档包（M4.0）以「评审通过」（用户）替代命令门禁。**门禁类型（与下文「期内子门禁是开工闸」对齐）**：M4.0–M4.4 **不是**期内子门禁，而是**期级门禁**——每个 M4.x 门禁一过即下一个 M4 子期可开工，故同时充当开工闸，须给 §14 勾稽与 docs 同步（与 M5.1–M5.3、M6.2–M6.3 那种不含勾稽的纯开工闸不同）；其中 **M4.4 是 v0.2.0 的发版闸**。M4 期 Go/No-Go 判据：M4.1 若 fork e2e 不达（分身未跑/回写丢/键漂移）→ No-Go 返工 WP2/WP3；M4.2 若 L3 审批拦截 fail-open → No-Go 返工 WP3（不接受「仅 hardline 拦截」降格）；M4.4 若回收 GC 无人工确认 → No-Go 返工 WP3。上文第 3 条的三命令口径及其 CLAUDE.md 失效引用在 M4.0-WP2 一并修正（改指 `CONTRIBUTING.md` 质量门禁节与「调度四条」）。[推演]

**M5–M7 期门禁口径（2026-11-20 追加）**：三期各期 M-gate 沿用五项框架，第 3 条质量命令统一为「调度四条」全绿：`make format-check` + `make spec` + `make lint` + `make release`（M4 已确立，M5–M7 沿用以保持口径一致；`make spec` 即 [Makefile](../../../../Makefile) 的 `spec: crystal spec`，全库统一写 `make spec`）；**纯文档包以「评审通过」替代命令门禁，限下列三个（本段只覆盖 M5–M7；M4 的纯文档包 M4.0 已在上一段 M4 口径中豁免）**：M5.0-WP1（领域对象/状态机文档）、M6.0-WP1（适配器契约文档）、M7.0-WP1（投影/撤销批次契约文档）。**门禁类型**：M5–M7 每期含 5 个子期（M5.0–M5.4 / M6.0–M6.4 / M7.0–M7.2），门禁分两类，**不要混称「各期 M-gate」**——

- **期级门禁**（M5.0、M5.4、M6.0、M6.4、M7.0、M7.2，共六处；M4 侧的 M4.0–M4.4 同属此类）：须给 §14 勾稽 + docs 同步 + 独立 gate 文档（`m5-gate.md`/`m6-gate.md`/`m7-gate.md`）。
- **期内子门禁**（M5.1、M5.2、M5.3、M6.1、M6.2、M6.3、M7.1 的收尾门禁，共七处）：纯开工闸——只判「下一子期能否开工」，证据即该子期各包的 WP 验收（spec 全绿 + 交付物存在 + 该子期「依赖」行所列前置包已完工），**不做 §14 勾稽、不出独立 gate 文档**，证据记入该期 gate 文档草稿的对应小节。

**发版闸 = 各期最后一子期的期级门禁**：v0.2.0 在 M4.4，v0.3.0 在 M5.4，v0.4.0 在 M6.4，v0.5.0 在 M7.2；这四处除期级门禁外还须满足 B.9.5 的版本门槛。

表内两条要点：**M6.2 与 M7.2 的开工闸分别是 M6.1 与 M7.1 的期内子门禁**（不是「第三节首子期」也不是期级门禁），WBS 里 `M6.2-WP1 依赖 M6.1-WP2`、`M7.2-WP1 依赖 M7.1 门禁` 与本表一致；**M6.1 与 M7.1 的收尾门禁即本表定义的期内子门禁**，只判开工、不出独立 gate 文档。**M5.0-WP2 不属纯文档包**——它同时交付 `src/platform/time_semantics.cr` 与 `spec/platform/time_semantics_spec.cr`，其 spec 全绿是 M5.1 的开工闸，同时参与 M5.0 期门禁的第 3 条；**调度四条任一红 → M5.0 判 No-Go，且 WP2 不算完工 → M5.1 不得开工**（WP2「完工」的定义就是 M5.0 期门禁通过，含文档评审）。两闸判定标准不同（M5.0 看文档评审 + 调度四条，M5.1 看 spec + WP2 完工），可以出现「M5.0 已过而 M5.1 仍需等」的差异，但不会出现「M5.0 No-Go 而 M5.1 可开工」（统一口径见 M5.0-WP2 验收条的说明）。**期门禁新增两条硬约束**：

6. **未实测不计入验收**：M6.4 涉及的 provider 若无真机 round-trip 证据，只能计「引擎/回放就绪」，产品面须标「实验/未验证」，并记入 design.md §15.1 口径；未实测越界当已测即 No-Go。**M7.1 同理但账户不同**：M6 用 E.1#9 的**只读**账户，M7 用 E.1#11 的**写权限**账户（专职 Sebas 日历 + 写 scope + 可清理撤销验证日历，明确不复用 E.1#9），两者不可互相顶替；E.1#11 未就绪时 M7.1-WP1 只交「写路径 + 幂等 spec（假 provider 回放）」，M7 门禁列未验证项、**不发 v0.5.0**（口径详 M7.0-WP1 与 M7.1-WP1 的「写权限账户依赖」段）。
7. **非目标拒绝口径**：任何包若引入提案 §8 所列非目标（全功能日历、默认全量双向、自动重排多人会议、以红点代替处理、把送达当完成），验收直接 No-Go，不接受「先实现再收敛」。

阶段门禁 Go/No-Go 判据：**M5** 若「同意图最多一个未决通知」仅靠应用层检查而无 DB 约束、或「无变化连续三轮零投递」不成立 → No-Go 返工 WP1-2/WP2-1；**M6** 若外部变化直接改动 WorkSession 或直接发通知（绕过评估器）→ No-Go 返工 WP3-1，不接受「仅同步层无副作用」降格；**M7** 若整批撤销失败时界面仍报全成功，或投影写入无幂等键 → No-Go 返工 WP1-1/WP1-2。[推演]

**期内子门禁的效力裁断（M5.1/M5.2/M5.3、M6.1/M6.2/M6.3、M7.1 等「{Mx.y} 门禁」字样）**：期内子门禁是**纯开工闸**而非发版闸——作用是「下一个子期能否开工」，判定材料只需该子期各包的 WP 验收证据齐全（spec 全绿 + 交付物存在 + 该子期依赖行所列前置包已完工），**不含**真机 round-trip、不做 §14 勾稽、不出独立 gate 文档。**期级门禁**（清单见上文「门禁类型」：M5.0/M5.4/M6.0/M6.4/M7.0/M7.2，M4.0–M4.4 同属此类）才须给 §14 勾稽 + docs 同步 + 独立 gate 文档。**谁当开工闸，逐子期见上文「开工闸逐子期对照表」**（M5.1←M5.0 期级、M5.2←M5.1、M5.3←M5.2、M5.4←M5.3、M6.1←M6.0 期级、M6.2←M6.1、M6.3←M6.2、M6.4←M6.3、M7.1←M7.0 期级、M7.2←M7.1），其中**六个期级门禁含勾稽、七个期内子门禁不含**。**发版闸**只有 v0.2.0→M4.4、v0.3.0→M5.4、v0.4.0→M6.4、v0.5.0→M7.2 四处，才适用五项 + 两条硬约束 + B.9.5 版本门槛。这样 M6.2→M6.3→M6.4 与 M7.1→M7.2 的依赖链同 B.3 第 6 条不冲突。[推演]

**M5.3 开工闸：冻结态 M5.2-WP2 是否满足（CodeRabbit 问）**：**满足，可开工**——WP2 交出「真实联动」或「冻结断言（Source 扩展 + 接口冻结断言，无真实联动）」任一形态都构成 M5.3 的开工条件。若是冻结断言，**开工前只需落一条文档前置**：①M5.2-WP2 的交付物与 `m5-gate.md` 草稿已写明「提醒未并入 admission 批次与字节预算」并登记 E.1#8 为未满足项（文档类证据，本包自身即可产出）。**产品面（Today/提醒 UI）的显式标注不进开工闸**——Today 与提醒的渲染归 M5.3-WP2（#74）与 M5.2-WP4（#72），要求它在 M5.3 开工前出现会形成「等到能写标注的包开工才允许开工」的死结；该标注改为**发版闸条件**，在 M5.4-WP1（#77）的三条件中复核。**开工闸与发版闸分离**：即便冻结态开工，v0.3.0 仍须在 M5.4-WP1 复核三条件（文档单列 + 产品面标注 + §15.1 记录）齐备；缺任一条件只挡发版，不回退 M5.3。[推演]

**M6.2 开工闸的构成与 CalDAV 顺延口径（CodeRabbit 问）**：M6.2 门禁 = 下列三项同时成立，缺一即 M6.3 不得开工：①三 provider 适配器的**回放 spec 全绿**（录制文件入库、可离线重放）；②`calendar-adapter-contract.md` 中的**能力矩阵草表**逐格填实，无「假设支持」空格；③三 provider 的**同步元数据映射表**（六类元数据 → 各家字段）写完并与 M6.1-WP2 的游标二元组对齐。**真机实测不进 M6.2 门禁**，一律归 M6.4——因此「M6.2 回放通过」不构成「已实测」。**CalDAV 顺延口径**：若 M6.2-WP1 拆去 v0.4.1，M6.3 的开工闸改判为「Google + Graph 两家的 ①②③ 成立」即可，**不要求 M6.2-WP1**；随 CalDAV 一并移入 v0.4.1 的条目是 M6.2-WP1（CalDAV 适配器）与其在 M6.4 中的真机 round-trip 段及对应矩阵行，其余（M6.2-WP2/WP3、M6.3、M6.4 的 Google/Graph 段）留在 v0.4.0 不动。[推演]
