## B.9 M5–M7 期排期、执行分块与版本计划（2026-11-20 追加）

> 本节对应承诺与日历、对话式 TUI 与应用根目录三份提案的落地排期：[commitments-calendar-integration.md](../../proposals/commitments-calendar-integration.md)、[tui-conversational-console.md](../../proposals/tui-conversational-console.md)、[sebas-home.md](../../proposals/sebas-home.md)。
>
> **周号口径**：
>
> - 上限累加以 M0–M4 合计 143 pd ≈ 28.6 周为旧基线：M5=W29、M6=W36、M7=W45；下限起点为 W19/W23/W29，本节不采用。
> - B.9.2/B.9.3 使用期内相对周号；例如 `M5-W1` 是 M5 开工后首个工作周，不与旧全局基线混算。
> - 容量 5 pd/周，溢出顺延下一块，不压缩范围。M6.5 的 6–9 pd 占用同一单人容量，串行排在日历工作之后。
> - 2026-11-27 追加 M5.0-WP3（1–2 pd）：原承诺链 W1–W7 保持，新增 W8 路径块，发版移至 W9。M5 后续全局周号及 M6/M7 起点待整体重排，不以单包加算术冒充完整容量裁决。
> **M5 起点为何取 W29 而不是更早**：不是因为 DAG 有跨期依赖（M5 对 M4 的唯一跨期长边只有 M5.0-WP2 复用 design.md §14 同一张表，见 B.1 跨期长边），而是**单人全职排期 + 上限口径取保守值**——M0–M4 未清前无并行人力，且 v0.3.0 与 v0.2.0 分属两条互不阻塞的版本线（B.9.5 已写明 v0.3.0 与 M6 解耦）。实际若按 M0–M4 下限推进，M5 可在 W19 开工，本节的 W29 是排期上界。[推演]

### B.9.4 算术自查

包合计=期合计：M5.0 原有语义两包下 1+1=2 / 上 1.5+1.5=3；追加 #278 路径包 1–2 后为 **3–5 pd、3 包**，但**期级语义闸仍只由 WP1/WP2 构成**——WP3 单独在其所在执行块验收，不并入 M5.0 的文档评审或 M5.1 开工闸。M5.1 下 1+2+3+2=8 / 上 2+3+5+3=13；M5.2 下 2+1+2+1=6 / 上 3+2+3+2=10；M5.3 下 1+1+2+1=5 / 上 2+2+3+1=8；M5.4 下 1 / 上 2 → **M5 = 23–38 pd，16 包**。
M6.0 下 1 / 上 2；M6.1 下 2+3=5 / 上 3+5=8；M6.2 下 3+3+3=9 / 上 5+5+5=15；M6.3 下 2+1=3 / 上 3+2=5；M6.4 下 2 / 上 4；M6.5 下 0.5+0.5+1+1.5+1.5+0.5+0.5=6 / 上 1+1+1.5+2+2+1+0.5=9 → **M6 = 26–43 pd，16 包**。
M7.0 下 1 / 上 1；M7.1 下 2+2=4 / 上 4+3=7；M7.2 下 1 / 上 2 → **M7 = 6–10 pd，4 包**。
**三段合计 55–91 pd、36 包，每包 ≤5 pd**（M5.1-WP3 与 M6.2 三包取 5 pd 上限，其余 ≤4）✓。

块-包对账与容量口径：

- **M5**：16 包 = W1×3 + W2×2 + W3×1 + W4×2 + W5×2 + W6×2 + W7×2 + W8×1 + W9×1 = 16 ✓。
- **M6**：16 包 = 日历 9 包（W1×2 + W2×1 + W3×1 + W4×1 + W5×1 + W6×2 + W7×1）+ M6.5 7 包（W8×4 + W9×3）✓。M6.5 占同一单人容量，W8 上限溢出 0.5 pd 由 W9 吸收，无并行压缩。
- **M7**：4 包 = W1×2 + W2×2 = 4 ✓。
- **溢出链**：M5-W2 超 3、W3 超 1、W4 超 1、W5 超 1，逐块传递后在 M5-W6 收敛；只顺延日期，不压缩 spec 范围。
- **块容量**：M5-W7（≤4）、M5-W8（≤2）与 M6/M7 全部块上限 ≤5 pd ✓。
周换算：23/5=4.6、38/5=7.6 → **5–8 周**；26/5=5.2、43/5=8.6 → **5–9 周**；6/5=1.2、10/5=2 → **1.5–2 周**；三期合计 11–18.2 → **11–19 周**。执行块表 9+9+2=20 块（含门禁/验证留白）；M6.5 占用 M6-W8/W9 的单人容量，不做并行压缩 ✓。
全程序：M0–M4 91.5–143 + M5–M7 55–91 = **146.5–234 pd**（M0–M7 口径）。M3 追加、M6.5 TUI 与 M8 的逐期区间见 [B.2](weekly.md)；三处口径并不构成同一张精算表，故本文件不另给「含全部追加」的全局总数。上限口径 M5-W1=W29、M6-W1=W36、M6-W9=W44、M7-W1=W45 仍是追加前的旧全局周号；新增 M5.0-WP3 后须整体重排，不能继续当作已批准的新时间线。

milestone 口径：
1. **一座版本一座 milestone**（v0.3.0 / v0.4.0 / v0.5.0），描述模板照 #2（目标/门禁/周期/发版/范围）。
2. **期父卡挂 milestone，子卡随父卡**：issue 侧建 3 张父卡（M5/M6/M7 各一）+ 36 张工作包子卡（=B.9.1 的 36 包；M6.5 另设期子卡 #263 管理其 7 张 WP 子卡），父子关系用 sub-issues 建立，子卡 milestone 与父卡一致。
3. **不并入 v0.2.0**：该 milestone 尚有 fork/join 轨 29 张未清，混入会让发版门禁不可控（B.2 的 M4 期边界串行同理）。
4. **发版动作**：milestone 内 issue 清零 → 打 tag（`v0.3.0`/`v0.4.0`/`v0.5.0`）触发既有 release workflow [来源: 仓库:CLAUDE.md 发版口径]；src/version.cr 与 CHANGELOG 同批改。
5. **已发布到 GitHub（2026-11-20；M6.5 于 2026-11-27 追加）**：milestone #3 `v0.3.0 (承诺与提醒闭环)`（16 卡：父卡 #91 + M5.0–M5.4 共 15 子卡 #63–#77）、#4 `v0.4.0 (外部日历只读镜像与重估 + 对话式 TUI)`（父卡 #92 + 日历子卡 #78–#86 + M6.5 期子卡 #263 与 WP #264–#270）、#5 `v0.5.0 (受控投影与撤销审计)`（5 卡：父卡 #93 + #87–#90）；sub-issues 关系按父卡—期子卡—WP 子卡分层建立。
